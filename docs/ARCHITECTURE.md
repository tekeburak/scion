# Architecture

This document describes the target architecture. Phase numbers refer to the roadmap in
[`ROADMAP.md`](ROADMAP.md). Anything that does not exist yet is marked *planned* with its phase;
everything else is built. "The reference design" is the internal system Anthropic describes in
[*Redesigning source control at Anthropic*](https://www.anthropic.com/research/redesigning-source-control),
which inspired Scion; [the FAQ](FAQ.md#how-does-scion-relate-to-anthropics-post) says where
Scion follows it and where it departs.

## Principles

1. **Clients are always online.** The client never needs a complete copy of the repository; it
   fetches what it needs when it needs it.
2. **Client–server asymmetry.** The server answers questions about history and blame, creates
   changesets, and performs merges and rebases. The client lays out files, watches the working
   copy, keeps a bounded object cache, and is otherwise thin.
3. **Everything the client can ask, any job can ask.** All source-control queries are RPCs. CI
   and tooling usually need no working copy at all.
4. **Horizontally scalable, no materialized copy anywhere.** Servers and caches are stateless
   apart from the metadata database and the object store. There are no packfiles and no
   repository maintenance.
5. **Commits are cheap, incremental and lock-free.** The cost of creating a changeset and its
   derived data scales with the size of the change, not the repository. Server-side refs are
   limited to `main` and `release/*`.
6. **The working copy is optional and sparse by design.**

### Two planes, one object protocol

The **control plane** is only served by `scion-server`: creating changesets, reading refs,
diffs, merge-base, blame, landing through change requests.

The **object plane** serves immutable trees and blobs by id. `scion-daemon`, `scion-cache` and
`scion-server` all implement the same `ObjectService` (today only the server exists; the other
two are Phase 4), so a client does not need to know the
topology; configuration decides which tier it talks to. Tiering is nevertheless strictly
enforced (daemon → cache → server) to isolate failure domains: a regional cache outage must not
turn into a thundering herd on the origin.

The negotiation is deliberately simple. The client never tells the server what it already has.
Starting from a root tree id it requests missing trees, then missing blobs, in batches:
`GetObjects` takes up to 256 ids per call and, for a directory the sparse profile takes whole,
returns every tree beneath it too, so a full clone of the 2,330-file benchmark slice is 12
requests. A commit goes the other way: the client hashes its files, asks `HasBlobs` which
contents the server already holds and sends only the rest in one `PutBlobs` stream. Every
request names specific immutable objects, so any tier can answer from cache, the exchange is
resumable, and there is no delta compression or packfile generation anywhere.

### Storage

- **Metadata** (Postgres; CockroachDB is a drop-in target): the changeset write-ahead log,
  `file_changes`, refs (one row each, moved by compare-and-swap on a version column), derived
  data pointers, trees and path-history pages (immutable, content-addressed rows, their bytes
  stored with Postgres's lz4 column compression), change requests, ingestion checkpoints. Schema: `migrations/`.
- **Objects** (S3-compatible via the `object_store` crate; GCS/Azure/local disk also work):
  `blobs/{id}`, `snapshots/{repo}/{changeset}.manifest`. All keys are immutable and
  zstd-compressed.

Trees live in the metadata database, as in the reference design, since Phase 10.3;
`docs/DATA_MODEL.md` explains why they first lived in the object store and what that cost.

The local development stack (`deploy/docker-compose.yml`) uses RustFS rather than MinIO as the
S3-compatible server because MinIO no longer publishes pullable community container images
(Docker Hub and quay.io both refuse the pull as of October 2026), while RustFS is Apache-2.0 and
actively published; the code is backend-agnostic, so any S3-compatible service works.

### Derived data

A changeset records only what changed, so blame, path history and ancestry questions need
indexes. Each derived-data type implements one trait whose `derive` takes the changeset and the
type's value for each parent — the definition is recursive. Types can be computed eagerly on
commit or lazily on first request (`CreateChangeset` derives what clone, log and diff need;
blame is lazy). Because the client never sees these structures, they can be replaced
without a client change.

A type whose value is missing for a changeset (a cold history, or every changeset after its
`VERSION` is bumped) is derived for the underived ancestors first, parents before children,
stopping at stored values. The walk holds every underived ancestor as an id only, at most 64
changesets at once (the rest are read again in batches of 64 when their turn comes) and a
value only until every child that reads it is derived, so its memory follows the frontier of
the history, not its length. `scion-server backfill <repo> <type>` runs that walk from every
ref for `root_tree`, `path_history` or `skip_list`, so the first request after a bump does not
pay for the whole history; each value is stored as it is derived, so an interrupted backfill
resumes where it stopped and a finished one is a no-op.

Types (phase 2): `RootTree`, `PathHistory`, `Blame`, `SkipList`. Later: copy detection,
basename/suffix indexes for path search.

Creating changesets has one code path, `scion_server::create_changesets`, which takes a batch:
`CreateChangeset` passes a batch of one, and the git importer (Phase 6.11) passes up to 64
uploaded commits at a time. Three things run at once: the batch's changesets are stored in one
transaction, its trees and path-history pages are derived and written concurrently, and its
skip lists (pointers only) are derived. Its derived-data pointers follow in one more statement,
so no pointer names a missing object, and a batch costs a few round trips however many
changesets it holds. `PathHistory` mirrors the
root tree with one history node per directory, but the nodes one changeset rewrites are stored
together, children before parents, in pages of about 16 KiB, one row of the `pages` table
per page: a one-file change writes one history page however deep the file is.

Every history entry also names the node its last change replaced (its directory's node at
that changeset's first parent), carried along unchanged while the entry is. A path's log is
therefore one lookup at the head and then one history-node read per change to that path,
never a scan of the changeset log. Those reads need not wait on each other: an entry also
counts the changes before it on its chain and names the node holding the change at the last
multiple of 16 below it (its anchor, computed from the previous entry without a read). A log
follows the anchors and advances the segments between them in lockstep, reading every page a
step needs in one query, so a thousand changes cost about 80 queries in sequence rather than a
thousand. A head's history never changes, so the server also remembers each `PathLog` reply
(up to 64 MiB of them) and answers a repeated log from memory.

`Blame` does not read its parents' values, so deriving it skips the ancestor walk that other
types need. A changeset's blame node holds the files it changed; each is attributed along its
own version chain, found through those same pointers (or `copy_from`), back to the newest
version whose blame is stored or to the file's creation. The chain's changesets and stored
blame pointers are read in batches of one metadata query each, the versions' contents
concurrently, and the line diffs between consecutive versions (a histogram diff) on the
blocking pool in parallel; only applying them to the attribution runs in order. Only the
requested changeset's node is stored, so a cold blame costs the versions of the files that
changeset touched, not the history.

### Landing changes

**What `scn` does.** `scn land` submits the current head as a change request and waits for
the outcome in the same call: the server holds the reply until the land worker finishes the
request, up to 20 seconds (below the client's 30-second deadline), and a client still waiting
after that asks again with `GetChangeRequest`. A fast-forward therefore lands in one round
trip, through the same worker as everything else; `scn commit --land` goes further and creates
the changeset and submits it in one `CommitAndLand` call. A head the worker rebased lands as a new
changeset, and the working copy moves to it so the next commit builds on what landed. A
conflict prints the paths and leaves `main` and the working copy untouched; `--no-wait`
prints the request id and `scn land --status <id>` reads it. `scn update` rebases ahead of
landing: the `Rebase` RPC replays the head's first-parent changesets that the target lacks
onto it through `scion_core::rebase`, creating each through the shared create path, skipping
any whose changes are already there, and stops at the first conflict with its paths, before
the working copy changes. `scn update --conflicts` resolves such a conflict locally instead:
the client asks for the merge base and the two diffs, moves the working copy to the target and
writes the head's changes on top, merged per file with `scion-diff3`, conflict markers where
both sides changed the same lines; the next `scn commit` turns the resolution into one
changeset on the target, which then lands as a fast-forward.
`scn explain-conflict [rev]` says why before anything moves: the `Rebase` RPC names the
conflicting paths (a clean one only leaves changesets nothing points to), and per path two
bounded `PathLog` reads list the changesets on each side since the path's last change at the
merge base, at most ten a side.

**Output for agents.** `scn --json` makes every command print one JSON document, and a
failure an error document whose `code` is the gRPC code's name for server refusals (as the
HTTP API spells it) or one of `scn`'s own (`conflict`, `needs_rebase`, `dirty`, …), with the
paths it is about. The schemas are hand-written JSON Schema files under `schemas/v1/`;
changesets and change requests have the HTTP API's shapes. A test runs every command with
`--json` and checks each document against its schema.

**Change requests on the server.** There is no CI-gated merge queue and no global repository
lock. `SubmitChangeRequest(repo, head)` records the request with `main`'s current changeset as
its base and returns at once, or, when asked to wait, once the worker has finished it; `GetChangeRequest(repo, id)` reads it back.
`ListChangeRequests(repo, status, limit)` returns the newest requests, of one status or of
any, by walking an index on `(repo, submitted_at)` or `(repo, status, submitted_at)`
backwards for `limit` rows; `scn requests` prints them. A request moves
through these states, stored in the `change_requests` table and scoped by `repo`:

| State | Meaning |
|---|---|
| `pending` | Waiting for the land worker. |
| `landing` | Claimed; being rebased onto `main` and landed. |
| `landed` | On `main` as `landed_cs`. |
| `needs_rebase` | Conflicts with `main` at the listed paths; `main` is untouched. |
| `rejected` | Rebased onto `main`, it would land nothing; or, with paths listed, it changes paths its submitter may not change. |

Each repository with requests gets one **serial land worker** inside `scion-server`, started
by its first submit (or at server start if requests are waiting) and woken by every later
submit. It claims the oldest `pending` request, rebases the head onto `main` through the same
rebase as `scn update`, and moves `main` with one compare-and-swap. A lost CAS happens only when
another writer (`MoveRef`, an import) moved `main`, so the rebased stack is replayed onto the
new `main`; every retry follows a move of `main`, never a timer. A conflict finishes the
request `needs_rebase` with its paths; nothing retries blindly. Moving `main` needs only the
rebased changesets' root trees and skip lists, so the worker derives just those; the path
history of what landed is stored by a task once the request is finished, off the worker's line.

**Pipelining.** While one request's compare-and-swap and its bookkeeping are in flight, the
worker already claims the next request and rebases it onto the `main` that swap will make.
When the swap succeeds, that rebase is the next request's starting point, so each land costs
one rebase rather than a rebase followed by the previous request's swap. When the swap is lost,
what was prepared for the next request assumed a `main` that never existed: it is dropped, the
current request is replayed onto the new `main` first, and requests still land strictly in
submission order. A finished request is broadcast to the clients waiting on it, so a waiting
`scn land` does not read it back from Postgres.

**Crash recovery.** Requests found `landing` when the server starts (with pipelining, the
request whose swap was in flight and the one claimed behind it) are landed again first, oldest
first.
That is idempotent because rebased changesets are content-addressed: a request stopped before
its CAS recreates the same ids, and one stopped after it first looks for its head, or the
rebased copy of it, on `main`'s first-parent line above the request's base (`main` may have
moved on since, through `MoveRef`), and is recorded `landed` there without replaying anything.

**`main` stays linear.** `main` only moves forward along its own first-parent line. A head
counts as a fast-forward of `main` only when `main` is on the head's first-parent line; a head
that reaches `main` only through a merge's other parent (a merge *of* `main` into a stack) is
replayed onto `main` like any other stack, so landing it never moves earlier `main`s off the
first-parent line that log, path history and blame follow.

**Simulation.** `scion-sim` runs one server on the memory stores in a single-threaded runtime,
with no network, and drives clients that commit, land, update, merge, revert and move `main`
directly, from a seed. The seed also decides how land workers and requests interleave (the
store yields to the scheduler before calls), which store calls fail (a stop between creating
the rebased stack and the CAS, or between the CAS and recording the outcome) and when the
server restarts (its runtime is dropped, stopping a land worker wherever it is). After each
run it checks that `main` only moved forward along its first-parent line, that every landed
request's change is on `main` exactly once, that nothing written was overwritten and that no
request was lost. `cargo test` runs 200 seeds; a failing one prints the command that replays
it, and the same seed replays the same history.

**When did X land.** `FindLanding(repo, changesets)` returns, for each changeset, the
`landed` request that put it on `main`, either as the request's head (a fast-forward) or as
the rebased changeset it landed as, with the time it landed. Partial indexes on
`(repo, landed_cs)` and `(repo, head_cs)` over landed rows make that one probe per changeset in
a single query, never a walk of `changesets` (invariant 1). `scn log --landed` asks it for every
changeset on the page. Only the top of a rebased stack is recorded as `landed_cs`, so the
changesets below it show no request.

**Server-side merge.** `Merge(repo, ours, theirs)` merges `theirs` into `ours` through
`scion_core::merge` against their merge base and creates a changeset with parents
`[ours, theirs]` whose file changes are against `ours` only (invariant 8), or returns the
conflicting paths and creates nothing; it creates nothing either when `ours` already contains
`theirs`. A file taken from `theirs` unchanged records `copy_from` (the same path, at
`theirs`), the provenance field every tracked change already has, so blame of that file follows
`theirs`' history, for instance to the `release/*` changeset that wrote a fix, while log and
path history stay on the first-parent line. `scn merge <rev>` merges a revision into the
working copy's head and moves the working copy to the merge, refusing local edits and changing
nothing on a conflict. Landing a merge is like landing anything else: when `main` has moved,
the rebase replays it against its first parent onto `main` and keeps its other parents.

**Server-side revert.** `Revert(repo, head, changeset)` creates a changeset on `head` that
puts every path `changeset` changed back as it was at `changeset`'s first parent, or returns
the paths that changed again between the two and creates nothing; `changeset` must be in
`head`'s history. It costs three path lookups per file the reverted changeset touched (at
`head`, at the changeset, at its parent), whatever lies between them. A restored file records
`copy_from` (the same path, at that parent), so blame keeps crediting its lines to the
changesets that wrote them rather than to the revert. `scn revert <rev>` reverts a revision
on the working copy's head and moves the working copy to the revert, refusing local edits;
landing it restores `main`'s tree from before the reverted change exactly when nothing else
landed in between.

Testing happens post-merge and pre-deploy.

### Snapshots and seeding

*Planned, Phase 4.* No manifest is written yet.

A snapshot is a **manifest**, not an archive: the set of tree and blob ids reachable from a
changeset's root tree (optionally per sparse profile), written to the object store. A new node's
daemon fetches the manifest and pulls the listed objects from its regional cache in parallel. No
tier ever holds a materialized copy of the repository.

### Identity and access

Every control and object request carries `authorization: Bearer <token>`,
and one interceptor in `scion-server` refuses a missing, altered, foreign or expired token
with UNAUTHENTICATED; health checks need none. A token is a principal and an expiry written
with the canonical primitives and signed with a keyed BLAKE3 MAC under the 32-byte server key
(`SCION_TOKEN_KEY`, without which the server does not start), so verifying one needs no
table. Each RPC then needs a role in the repository it names, from the `grants` table (`repo`,
`principal`, `path_prefix`, `role`; server-wide grants live under the reserved repository
`*`): `reader` for reads and the object plane (whose requests name a repository too, although
objects are shared), `writer` for `CreateChangeset`, `Rebase`, `Merge`, `Revert` and change
requests, `admin` for `MoveRef`, and a server-wide `admin` for `InitRepo`, which makes its
caller the new repository's admin. A missing role is PERMISSION_DENIED, also for a repository
that does not exist. A grant with a `path_prefix` holds its role only under that directory:
every path a `CreateChangeset`, `Merge`, `Revert` or `Rebase` would change must be under a
prefix where the caller is a writer, and `PathLog` and `Blame` need the path under one where it
is a reader, while `Diff` returns only such paths; a refusal names the first path outside.
Objects are fetched by id and checked per repository only, and `MoveRef` needs `admin` on the
whole repository. The land worker reads the submitter's grants (recorded with the request)
when it lands and holds the rebased stack to them, so a grant revoked since the submit counts
and a stack someone else created cannot widen what the submitter may change; such a request
ends `rejected` with the paths outside.

People sign in with **GitHub device-flow login** (`scn login <server>`). `LoginService`, the
one service that takes no token, runs the flow for the client: `StartLogin` asks GitHub for a
device code with the server's OAuth app (`SCION_GITHUB_CLIENT_ID`), `scn` shows the
verification URL and user code, and polls `FinishLogin`, which exchanges the code for a GitHub
access token, reads the user once and returns a 30-day token for `github:<login>`. The server
keeps no login state, and the GitHub access token is used once and dropped. `scn` stores the
token in `$XDG_CONFIG_HOME/scn/tokens/<server>` with mode 0600 and sends it, unless
`SCN_TOKEN` is set. A denied or expired code ends the login with a message that says which.

CI jobs and agents use **service principals** (`sp:<name>`) whose tokens the operator issues
with `scion-server` subcommands that work on the stores directly, with no server running:
`grant <repo|*> <principal> <role> [--path <dir>]`, `revoke <repo|*> <principal> [--path
<dir>]` and `token <principal> --ttl <duration>`; the same commands bootstrap the first admin.
After that, an admin of a whole repository manages its roles from a working copy: `scn access
grant <principal> <role> [--path <dir>]`, `revoke` and `list` call `Grant`, `Revoke` and
`ListGrants`, which check their input as the operator commands do. `scn whoami` calls
`WhoAmI`, which needs only a token, and shows the principal, the token's expiry and the
caller's grants in the working copy's repository.
Tokens are not revocable: one stays valid until its expiry (30 days for `scn login`, the
`--ttl` of `scion-server token`), and cutting someone off means revoking their grants, which
takes effect on their next request, since grants are read on every request and not cached in
the token. A server keeps each repository's grants, and separately its refs, in memory, but only
while it listens on Postgres `LISTEN` for the notification every grant or ref write sends, from
any process: a notification drops that repository's entry, and while the listening connection
is lost the server reads from Postgres and remembers nothing. Tokens are checked once, at the server boundary; tiers below the server will forward
them and never decide access themselves. Authorization is repo- and directory-scoped (`repo` is part of
every rule, invariant 7); moving `main` and `release/*` requires admin.

### Performance bar

Every benchmark runs the same workloads against git and against public implementations of
the same reference design, on the same machine. The bar, set by Phase 10, is that every
workload is a multiple faster than git: clone at or below 0.3× git's time, sparse clone 0.1×,
status 0.03×, warm path log 0.3×, warm blame 0.1×, commit + land 0.5×, 16 writers 0.1×, warm
import 0.5× and cold import at or below git. The cold, first-call `log` and `blame` of a
freshly started server are held within 2× git, because each pointer hop is a round trip to a
store that git reads from a local packfile; production servers are rarely cold, so the table
also reports "server warm, client cold". A regression of more than 20% on any row is a bug;
a nightly benchmark job that fails on one is planned. The workloads cover import, full and sparse checkout,
status, one-file commit, land, 16 writers landing at once, log and blame; the results are the
Benchmarks table and chart in `README.md`, rendered from `docs/bench-real.csv`, and the
measurement script (`scripts/bench-real`) stays in the repository. Toward the bar, trees
and history pages moved from the object store to the metadata database (as the reference design
keeps them), the object plane gained batch RPCs (`GetObjects`, `HasBlobs`, `PutBlobs`), landing
became one round trip (`CommitAndLand`, behind `scn commit --land`) and the land worker
prepares the next request while the previous one lands. Not every row meets the bar yet; the
Benchmarks table shows which, and `docs/ROADMAP.md` (Phase 10) lists the remaining steps.

### Web interface and agent API

The same binary serves a browser interface: `scion-server --web <addr>` runs `scion-web`'s
pages on a second listener, in process with the control plane, so a page reads the metadata
and object stores directly and no RPC sits between them. The pages are rendered on the server
(`maud` templates, no JavaScript): the repositories a principal holds a grant in, a
repository's home (`main`'s top directory, its refs and its README rendered from Markdown with
raw HTML shown as text), a directory or file at any ref or changeset, the first-parent log of
the repository or of a path (50 per page, the next page starting at the last one's parent),
blame, a changeset with its line diffs against its first parent (the first 20 files; text up to
1 MiB), and the change requests with their status, heads and conflicts. Every page needs a
reader of its repository, checked from `grants` like an RPC; a directory-scoped reader gets
log and blame only under its directories and a diff only of those paths, while trees and
files, like the object plane, need a reader of the repository only.

The token comes in `Authorization: Bearer <token>` or in the session cookie a browser gets by
signing in with GitHub's web flow, the browser sibling of `scn login`: `/login` sends it to
GitHub with a fresh state (a MAC of a counter and the time under the server key), also kept in
a ten-minute cookie, and `/login/callback` checks that GitHub sent the same state back before
it trades the code for a 30-day token of `github:<login>` with the OAuth app's client secret
(`SCION_GITHUB_CLIENT_SECRET`; the app's callback URL is `https://<host>/login/callback`).
The token goes into the `scion_session` cookie (`HttpOnly; Secure; SameSite=Lax`) and the
server keeps no session state; `/logout` drops the cookie, and the token, like every token,
stays valid until it expires. A repository is **public** when the reserved principal `anyone`
holds a `reader` grant in it (`scn access grant anyone reader`, or `--path` for one
directory): a visitor without a token reads what `anyone` may, and a signed-in one reads its
own grants and those of `anyone`, both from one read of the repository's grants. No token
names `anyone`, it can be granted nothing but `reader`, and the gRPC services do not read its
grants, so public reads exist only in the web interface and its HTTP API.

A page is bounded like an RPC: at most five metadata reads (the log adds one ancestry read per changeset it lists, the walk
the `Log` RPC also makes), a 30-second deadline, and a content policy that loads nothing but
the page's own style.

The same listener serves an **HTTP/JSON API** under `/api/v1` for clients that do not speak
gRPC (`docs/API.md` lists every route). It is a translation only: each route builds the RPC's
request, with the caller's principal from `Authorization: Bearer <token>`, and calls the same
`ControlService` or `ObjectService` method the gRPC services run, so roles, directory scopes,
validation and the land worker are shared; with `--web`, gRPC and HTTP run on one control
server, so a repository still has one land worker. Ids travel as hex, blobs as raw bytes,
and changesets and trees as JSON that the server turns into the canonical encoding before
hashing (invariant 5: no JSON is ever hashed). A `GET` without a token reads as `anyone`,
every read with one also holds `anyone`'s grants, and every other method needs a token. A
request has the pages' 30-second deadline and a body of up to the 64 MiB blob limit.

Agents reach the same API through **`scion-mcp`** (`docs/MCP.md`), a Model Context Protocol
server they start on stdio or reach as streamable HTTP. It is a client of the HTTP API with one
bearer token, never of the stores, so it adds no authorization of its own and runs anywhere an
agent does. Its tools name the agent's loop (`tree`, `read_file`, `log`, `blame`, `diff`,
`changeset`, `write_files_and_commit`, `land`, `change_request`, `list_repos`) and its
resources are `scion://<repo>/<path>@<revision>`. Reading a path walks one tree per
component from the revision's root tree, which `GET changesets/{id}` returns alongside the
changeset (derived data, not a changeset field); writing uploads the files' blobs and creates
one changeset on the parent, and `land` submits it and waits for the land worker.

A change request's page also **acts on it** for a signed-in member, through the RPCs `scn`
calls, so roles are checked as there; the page shows only the buttons the caller's role
allows. A writer rebases a request that needs a rebase onto `main`'s current changeset
(`Rebase`), which shows the rebased changeset or the paths that still conflict, and lands a
request that needs a rebase or was rejected by submitting its head again as itself and
waiting for the land worker (`SubmitChangeRequest`): an admin lands this way a change its
submitter's directory grants did not cover. The submitter or an admin rejects a request that
is `pending` or `needs_rebase`, one conditional update in `change_requests`, which a request
the land worker has claimed already does not match. Actions are `POST`s; the session cookie
is `SameSite=Lax`, so a browser sends it only from this site, and a `POST` whose `Origin`
names another host is refused as well. A separate code-review product is not a goal;
change-request pages are.

The pages also **create and administer repositories**, again through the RPCs `scn` calls: a
signed-in server admin creates one from the repository list (`InitRepo`, as `scn init`, its
creator its admin), and a repository's settings page, for an admin of all of it, lists its
grants and grants and revokes roles (`Grant`, `Revoke`, as `scn access`; the server checks the
form's principal, role and directory as it checks the command line). Making a repository
public or private is a grant or revoke of `reader` to `anyone`.

### Ingestion

`scion-ingest` (phase 6) is the only way history enters Scion from git; there is no git wire
protocol. Like `scion-server` it is an operator tool that works on Postgres and the object
store directly (`DATABASE_URL`, `AWS_*`) and creates changesets through the same code path as
`CreateChangeset`, so eager derivation and every server-side check apply unchanged.
`scion-ingest import <git-dir> <repo> [<rev>]` imports every commit reachable from `<rev>`
(default `HEAD`), parents before children, into a repository created with `scn init`; it never
creates one, and an unknown name is refused before anything is uploaded; `scion-ingest verify <git-dir> <repo> [--sample <n>]`
compares each imported tree with the git tree by path, file kind and content and names the
first path that differs.

**Mapping.** One changeset per git commit. `parents` keeps every git parent in order, but
`file_changes` is the tree diff against the first parent only (the empty tree for a root
commit), per invariant 8. A file added in a commit that also deletes or changes a file with the
same content, or with at least half its lines, records that file as `copy_from` at the first
parent, so `blame` follows renames and copies. Git modes map to `FileType` (regular,
executable, symlink). Author and committer keep their own dates and UTC offsets; names, emails
and the message are read as UTF-8 with invalid bytes replaced. The commit's raw sha goes into
`extra["git-sha"]`: provenance, not a field (invariant 4). The only ref an import creates or
moves is `main` (invariant 6), by compare-and-swap once every changeset exists. While `main`
is still at the empty root `scn init` created, the first import replaces it rather than
fast-forwarding: a git root commit has no parent, so the imported history does not descend
from that root, which stays stored like every changeset.

**Rejected.** A submodule (gitlink) entry, a path that is not a valid `RepoPath` (not UTF-8,
or with a `.` or `..` component) and a blob over the server's per-blob limit (64 MiB)
stop the import with an error naming the commit and path. Nothing is rewritten to make such a
commit fit; the history has to be fixed in git first.

**Resume.** Each created batch of changesets is recorded in `ingest_checkpoints`
(`repo`, git sha → changeset id) right after its derived data is stored. A run skips every
commit already recorded, so an interrupted import is resumed by running the same command
again: it creates exactly the remaining commits and ends at the same `main` as an
uninterrupted run. Changeset ids are content hashes, so a commit that was created but not yet
checkpointed is created again as the same changeset.

**Incremental sync.** Running `import` again against an updated repository imports only the
new commits and fast-forwards `main`; importing at X and then at Y gives the same changeset ids
as one import at Y. If `main` points at a commit the new revision does not contain (the
upstream history was rewritten), the import fails naming that commit and writes nothing. A
`main` that has moved past the import, because changes were landed on it, is refused the same
way: Scion is then the source of truth and git is no longer imported into it.

**Bounded memory.** Commits are mapped on one thread, their blobs uploaded concurrently (one
presence check per commit, then only the missing blobs), and the uploaded ones created in order
in batches. Only commits in flight are held, so memory follows the largest commit, not the
history.

`scion-ingest` reads git repositories with `gix` (pure Rust, `zlib-rs`, no network features);
the dependency stays in that crate so no other crate builds it.

## Non-goals (first 12 months)

git wire compatibility (import only); offline operation; a separate code-review product beyond
the change-request pages of the web interface; Windows; garbage collection of unreachable
objects; large-file chunking (there is a per-blob size limit); ignore files (sparse profiles and
explicit `add` instead); branch-like server refs.
